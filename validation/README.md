# Exact packaged-JAR validation

This directory is a separate NeoForge 1.21.1 validation project. Its only
source-set mod is `exact_jar_validation`. A candidate port is installed as
`build/validation-runtime/<lane>/mods/target-under-test.jar`; it is never added
to this project's source sets or compile dependencies.

The runtime check binds the target mod ID to the owning file reported by
NeoForge `ModList`, requires that file to be the staged regular JAR, and
recomputes its SHA-256. The clean `mods` directory must contain exactly that
one JAR. Required dependency mods may be resolved on ModDevGradle's runtime
classpath through exact coordinates in the target config.

The receipt also records the loaded mod IDs and versions and fingerprints
their regular JAR containers reported by NeoForge `ModList`, including runtime
dependencies.

## Validation boundary

The dedicated-server lane proves packaged-JAR origin, normal server readiness,
a controlled native stop, an overworld save after the stop request, and
complete shutdown.

The client lane uses one hidden client process and one copied pristine world
for four ordered scenarios:

1. `target-jar-origin`
2. `client-world-ready`
3. `creative-inventory-rendered`
4. `mod-creative-tabs-all-rows-rendered`

The client opens the inventory through its registered key binding. Every
creative row is scrolled through the real `CreativeModeInventoryScreen`
input handler and accepted only after a later client tick and
`ScreenEvent.Render.Post`. The 45 visible item slots must match the expected
slice of the selected tab by count plus
`ItemStack.isSameItemSameComponents`. Persistent component-codec SHA-256
values are portable evidence only; native equality remains authoritative, and
transient patch and effective component IDs are listed explicitly.

The harness captures an immutable PNG for every rendered row. Every occupied
slot among the first 45 creative slots must have a decoded nonblank icon; only
a pinned target item may use a source-backed exception. Per-row and global
occupied/target accounting must be exact. The harness then resets the scroll
position, uses the screen's native close path, and verifies the client and
integrated-server player inventory, selected slot, carried stack, and menu
state against server-thread and client-thread baselines across later client
and server tick fences. It creates no entities, blocks, items, commands, or
slot clicks. The receipt is sealed after the integrated server reports an
overworld save and `ServerStoppedEvent`.

This scope covers boot, server/client world loading, creative inventory
rendering and strict logs. It does not claim detailed wand or item behavior.

## Configuration

Copy the target template to the ignored `target-local.properties`, then fill `targetJarPath`, `targetJarSha256`, and `pristineWorldPath` from
`targets/constructionwand.properties` or `targets/sakura.properties`.
Use forward slashes in configured paths, including Windows paths such as
`E:/artifacts/candidate.jar`, so PowerShell and Java property parsing are
identical.

`pristineWorldPath` must point to an owned read-only Minecraft 1.21.1 vanilla
creative save generated by a normal dedicated-server boot and controlled
`stop`. It must not be a real user save. The path is never modified. Its files
must match `fixtures/client-world.manifest.json`; `session.lock` is excluded.
The launcher repeats the exact file-set, size, and SHA-256 check after the
client exits and seals that result into the unique run evidence.

The source-controlled target files intentionally leave candidate paths and
hashes blank until the exact packaged artifacts exist. Staging fails before
launch when any required value is absent or mismatched.

## Project-owned runtime session

The validation project contains its own public runtime adapter:
`scripts/Invoke-ModporterRuntimeSession.ps1`,
`scripts/runtime_process_inventory.ps1`, and
`gradle/modporter-testing.gradle`. It does not require a private testing
framework, a GitHub login, or network access. A private local gate may run
separately when explicitly configured, but it is not part of this validation
contract.

`Invoke-Validation.ps1` acquires a lease keyed to the canonical
`build/validation-runtime/<lane>` directory, refuses a scoped live Minecraft
process, assigns `MINECRAFT_MOD_TEST_SESSION_ID`, and starts the existing hidden
desktop adapter. The adapter invokes the checked-in Gradle wrapper through
`scripts/run_gradle.py`. The session accepts success only when the immutable
harness receipt has the exact requested and observed scenario order, expected
process/world counts, successful per-scenario cleanup, and a complete runtime
exit:

```powershell
pwsh -NoProfile -File scripts/Invoke-Validation.ps1 `
  -Lane server `
  -TargetConfig target-local.properties `
  -OriginalSourceRoot E:/source/pinned-upstream

pwsh -NoProfile -File scripts/Invoke-Validation.ps1 `
  -Lane client `
  -TargetConfig target-local.properties `
  -OriginalSourceRoot E:/source/pinned-upstream
```

Use `targets/sakura.properties` for the Sakura research candidate. Its required
Mysterious Mountain Lib coordinate is loaded outside the clean `mods`
directory.

Each invocation requires the original upstream repository at its exact pinned
commit. Before launch, a read-only Git gate disables optional locks, requires
the pinned commit/tree and origin, refuses dirty tracked/index/untracked
derivation inputs, derives IDs from the exact pinned blobs, and binds every
blob/worktree hash plus the ordered ID digest into an immutable baseline
receipt.

Each invocation creates a unique immutable directory below
`build/validation-evidence/`. It refuses any pre-existing output instead of
deleting or overwriting it. The runtime lease remains bound to the
actual fixed `build/validation-runtime/<lane>` game directory.

Each lane writes:

- the in-game immutable harness receipt in the unique evidence directory;
- the immutable original-source baseline receipt for the pinned repository,
  commit, tree, derivation blob hashes, and exact ordered item IDs;
- the immutable pre-launch staging receipt for the exact config, target JAR,
  clean `mods` count, client fixture source, and original-source baseline;
- a complete SHA-256 manifest of the validation project sources and public
  runtime adapter, plus a post-run check that the manifest root did not change;
- a public runtime-session receipt that binds the harness receipt SHA-256;
- a complete UTF-8 runtime log and a strict log-audit receipt; and
- a top-level run receipt that binds the target config, exit results, runtime
  log, staging receipt, harness receipt, runtime-session receipt, and audit
  receipts.

The client evidence additionally contains the complete creative-row trace,
one PNG and occupied-slot icon audit for every row, bounded client/server
player-state cleanup evidence, and the post-run pristine-world receipt.
Each lane also copies the saved `level.dat` into its immutable evidence root.
Their SHA-256 values are bound into the harness or run receipt.

The harness may be compiled independently, but no target JAR runtime result is
claimed until these immutable receipts all pass.
